## P1

### P1-A: Mobile hamburger tap triggers Precedents navigation (click-through bug)

**Route:** any mobile viewport (375px wide), tap hamburger to open drawer

**What happens:** Clicking the hamburger `<button>` (fixed, `z-60`, `top-3 left-3`)
dispatches a click that opens the drawer AND simultaneously triggers a navigation to
`/precedents`. The Precedents nav link slides into the button's hit area during the
200ms CSS translate animation; because the button and aside are in separate stacking
contexts (button `z-60`, aside `z-50`) a second synthetic or pointer event reaches
the link underneath.

Confirmed via:

- JS `dispatchEvent` click → `window.location.pathname` becomes `/precedents` at 300ms
- `asideX` at 200ms is `0` (drawer open) but page URL is already `/precedents`
- DOM geometry at 50ms into animation: `asideX: -178`, Precedents link `x: -170` —
  still off screen, so click-through may be due to the click event from the button
  bubbling into the transitioning aside before pointer-events settle.

**Fix direction:** Add `pointer-events-none` to the aside during the slide-in animation
(remove after `transitionend`), or add a short `pointer-events: none` to the entire
aside while `mobileOpen` transitions from false → true.

### P1-B: 404 on unknown top-level segments loses the app shell / sidebar

**Route:** `/nonexistent-page`

**What happens:** Next.js serves its default 404 error page — white background, no
sidebar, no QGI layout. The sidebar is completely absent.

**Comparison:** `/precedents/civil-war-and-insurgency` (unknown slug within the `(app)`
route group) DOES render the sidebar correctly because the layout wraps that segment.
A truly unknown top-level segment (`/nonexistent-page`) falls outside the `(app)` route
group and hits the Next.js root error boundary.

**Fix direction:** Add a `not-found.tsx` at the `(app)` group level (or at `app/`) that
renders inside the app layout, giving the user a styled 404 with sidebar intact and a
link back to `/dashboard`.

## P2

### P2-A: No `aria-current="page"` on the active sidebar link

**Source:** `Sidebar.tsx` line 534–548 (`NavLeafLink` component). The active link applies
visual styles (`color: var(--qgi-accent)`, `backgroundColor: var(--qgi-accent-glow)`) but
does not set `aria-current="page"`.

Screen readers therefore cannot identify the current page from the nav landmark. This was
flagged as a pre-existing gap in PR-i — confirming it is NOT introduced by this PR but
still open.

**Fix:** Add `aria-current={active ? "page" : undefined}` to the `<Link>` in
`NavLeafLink` (one line).

---

### P2-B: `<nav>` element missing `aria-label`; sidebar `<aside>` missing `aria-label`

**Source:** `Sidebar.tsx` line 451 — `<nav className="flex flex-col ...">` has no
`aria-label`. The wrapping `<aside>` (line 404) also has no `aria-label`.

Without a label, screen reader users hear "navigation" for the nav landmark and
"complementary" for the aside — no indication these are the primary site navigation.
WCAG 2.1 SC 4.1.2 advisory technique recommends labelling landmark regions when more
than one of the same type exists.

**Fix:** `<nav aria-label="Main navigation">` and `<aside aria-label="Site navigation">`.

---

### P2-C: Focus ring on sidebar nav links uses browser-default outline (low contrast)

**Observed:** `outline: auto 1px rgb(16, 16, 16)` — a near-black 1px outline on a dark
`var(--qgi-surface)` background. Technically present and `:focus-visible` matched, but
contrast is poor (dark ring on dark bg). The sidebar links have no Tailwind
`focus-visible:ring-*` or `focus-visible:outline-*` class.

**Fix:** Add `focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-[var(--qgi-accent)]`
to the `NavLeafLink` className to replace the browser default with a visible accent ring.

### P2-E: Hydration errors on `/precedents` and `/countries`

**`/precedents`:** `throwOnHydrationMismatch` — date rendered as `5/10/2026, 12:37:29 AM`
on client vs `10/05/2026, 00:37:29` on server. Root component: `WhatWereStillTesting`
`<p>` inside `PrecedentsMergedListClient`. Cause: locale-sensitive `Date.toLocaleString()`
called without a fixed locale on a server-rendered component.

**`/countries`:** Attribute-level hydration mismatch on the search `<input>` — server
renders `background-color: "var(--qgi-surface)"` (kebab-case) vs client
`backgroundColor: "var(--qgi-surface)"` (camelCase). Also `caret-color: transparent`
appears server-side but not client-side. Root: inline style object computed differently
in SSR vs hydration.

Both are pre-existing (not introduced by PR-i sidebar changes) but flagged here as they
produce console errors on every page load.
